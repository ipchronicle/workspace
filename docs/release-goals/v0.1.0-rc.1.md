# IPChronicle v0.1.0-rc.1 Release Goal

Status: Ready to execute

Target: First public release candidate

## Purpose

Bring IPChronicle from the completed Phase 2 control plane to a release-ready
`v0.1.0-rc.1` build. The result must be usable by an individual self-hosting
administrator, independently verifiable, and packaged for the supported Center
and Agent environments.

This file is the execution contract and definition of done for the goal. Keep
it unchanged while the goal is active. Track implementation progress in a
separate checklist or task system so that the completion criteria do not move
during execution.

## Starting Point

The product repository is `/root/ipchronicle-workspace/repos/ipchronicle` and
the workspace repository is `/root/ipchronicle-workspace`.

At the time this goal was prepared:

- product Phases 0, 1, and 2 were complete;
- the product repository baseline was commit `abcb4f8`;
- administrator persistence, authentication, Agent enrollment, configuration
  convergence, node inventory, and temporary Agent sync sessions were working;
- network-egress discovery, address observation, complete probes, historical
  interpretation, notifications, Agent updates, and release packaging remained
  to be implemented; and
- the workspace had an existing untracked `tmp/` directory that must not be
  modified, deleted, or committed as part of this goal.

Recheck both repositories before starting. Treat newer user changes as part of
the current baseline and never revert unrelated work.

## Required Product Scope

Complete Phases 3 through 7 of `docs/implementation-sequence.md` as end-to-end
vertical slices.

### Phase 3: Network Egress And Lightweight Observation

Implement Linux interface, route, address, lifecycle, and default-route
inventory; durable default and administrator-enabled egresses; local selector
availability; HTTP, HTTPS, and SOCKS5 proxy paths; encrypted proxy credentials;
native bounded public-address discovery; independent confirmation; NAT and
temporary-IPv6 interpretation; address transition, failure, recovery, offline
buffering, gap reporting; and the complete administrator workflows for those
capabilities.

### Phase 4: Complete Probe Vertical Slice

Implement stable node runs and per-egress executions, local scheduling,
address-change triggers, one-slot immediate tasks, fresh official IPQuality
downloads, root process-tree supervision, bounded output and diagnostics,
crash-consistent result publication, bounded per-egress queues, idempotent
Center ingestion, history-generation invalidation, and all manual, scheduled,
progress, partial-success, failure, raw-result, warning, and reset workflows.

### Phase 5: History, Interpretation, And Retention

Implement the fixed known-field catalog, explicit missing and incompatible
format states, chronological comparison, arbitrary snapshot comparison,
first-result baselines, starring, indefinite/age/logical-size retention,
dependency-safe cleanup, storage usage and overage reporting, history gaps, and
the complete bilingual history and comparison interface.

### Phase 6: Notification Delivery

Implement durable change and operational events, current-rule evaluation,
stable aggregation and delivery identities, Telegram and generic Webhook
senders, the isolated goja JavaScript sender, bounded concurrency and retries,
terminal retention, secret redaction, failure isolation, and real-equivalent
test delivery without sending unsolicited messages to real external recipients.

### Phase 7: Agent Updates And Release Readiness

Implement administrator-triggered Agent updates, platform and checksum
validation, atomic replacement, supervision, health commitment, rollback,
stable and RC discovery, semantic version and capability gates, release test
suites, multi-platform Center images, no-CGO Agent artifacts, checksums, SBOMs,
notices, source links, Compose assets, and standalone release documentation.

Do not stop merely because one phase or one useful internal build is complete.
Continue until every completion criterion in this file is satisfied or a true
decision boundary blocks progress.

## Non-Negotiable Boundaries

- The product serves one personal self-hosting administrator. Do not add
  multi-user, tenant, role, or public-result functionality.
- Keep the accepted single product repository and modular-monolith Center.
- Support a Docker Compose Center on Linux only. IPChronicle does not terminate
  TLS or configure an operator's reverse proxy.
- Support root Agents on Linux AMD64 and ARM64 with both systemd and OpenRC,
  including Alpine/musl. The Agent must remain free of CGO.
- Keep Agent communication outbound-only, with ordinary HTTP synchronization
  as the source of truth and temporary WebSocket sessions as wake-up hints.
- Model durable network egresses rather than arbitrary target IP addresses.
- Trust official GitHub and the official IPQuality download path as already
  accepted. Download a fresh upstream script for each attempted egress and
  validate its bounded JSON output; do not vendor or rewrite the upstream
  script in this release.
- Keep `config.db` and `history.db` separate according to their accepted
  ownership. `config.db` is never disposable history.
- Before the first stable release, development versions of `history.db` do not
  require backward compatibility under ADR 0050. Do not extend that exception
  to `config.db`, silent corruption recovery, or a published stable release.
- Preserve bounded Agent queues, one active node probe run, one immediate task
  slot, no task backlog, and the accepted skip/no-catch-up behavior.
- Use the contract-first OpenAPI boundary, generated bindings, Chi,
  `database/sql`, `sqlc`, goose, bbolt, official shadcn/ui source components,
  Tailwind utilities, and complete Simplified Chinese and English resources.
- Do not add placeholder success, silent fallback, broad error swallowing,
  duplicate sources of truth, unbounded queues, or unresolved behavior-affecting
  TODOs.
- Do not send real Telegram messages, Webhooks, or other external notifications
  during development. Use local or explicitly isolated receivers.
- Do not create paid resources or change production infrastructure.

## Execution And Change Management

Implement each slice with its OpenAPI contract, generated clients, domain
logic, persistence, migrations, Agent behavior, administrator interface,
failure states, and tests advancing together.

For every material slice:

1. State its invariants and expected failure behavior before implementation.
2. Inspect the owning modules and current Git state.
3. Implement the smallest complete vertical behavior without parallel legacy
   or placeholder paths.
4. Run focused tests while developing.
5. Run the repository gates required by the changed surface.
6. Inspect the diff for secrets, generated artifacts, unrelated edits,
   duplicated logic, weak failure handling, and undocumented behavior changes.
7. Commit a coherent change in the product repository and push it.
8. Wait for GitHub CI; diagnose and fix every failure before continuing.

Keep workspace documentation and product code in their separate repositories.
Commit accepted cross-cutting decisions only in the workspace repository. Do
not commit nested repository contents from the workspace root.

Safe local development actions include installing required toolchains and
dependencies, rebuilding Compose services, creating disposable test data, and
running upstream smoke tests. A test environment is not evidence of success
until its service, output, or observable behavior has been checked.

## Verification Requirements

At minimum, the final candidate must pass:

- `make check`;
- ordinary and race-enabled Go tests, including repeated critical concurrency
  tests where nondeterminism is plausible;
- `make compose-smoke` against the production Center image;
- `make browser-test` for desktop and mobile Chromium;
- generated OpenAPI, SQL, and frontend binding drift checks;
- committed-source secret scanning and `git diff --check`;
- deterministic network inventory, egress, address, NAT, proxy, scheduling,
  queue, ingestion, history, comparison, retention, notification, update, and
  rollback tests;
- install, reinstall, uninstall, upgrade, rollback, migration, history reset,
  Center outage, Agent restart, unavailable-selector, and queue-overflow tests;
- native or release-equivalent AMD64 and ARM64 validation for systemd and
  OpenRC, including Alpine/musl Agent operation;
- live upstream IPQuality smoke testing kept separate from deterministic JSON
  merge and schema-drift fixtures;
- the 256 MiB Agent, 512 MiB Center, 70-node, and 420-egress release gates; and
- inspection of important desktop and mobile UI states for overflow,
  occlusion, missing translations, and inaccessible controls.

Do not replace an unavailable release gate with a mock success. If a required
native environment or external service is temporarily unavailable, preserve
the failing or pending evidence and continue only with work that cannot conceal
that gap.

## Definition Of Done

The goal is complete only when all of the following are true:

1. Every required behavior in Phases 3 through 7 and the accepted first-release
   baseline is implemented without placeholder success or unapproved scope
   reduction.
2. All verification requirements above pass, with results recorded in the
   release-readiness report.
3. The release artifacts are reproducible from the exact candidate source and
   contain correct version, revision, checksum, SBOM, license, and source
   metadata.
4. A new individual operator can deploy the Center, enroll supported Agents,
   configure network egresses, observe addresses, run and schedule probes,
   inspect and compare history, configure retention and notifications, and
   perform an Agent update using only the published documentation.
5. Both repositories have been inspected. The product repository is clean,
   every goal-related commit is pushed, and the final GitHub CI run succeeds.
   The workspace contains no accidental product source, secrets, generated
   artifacts, or changes to the existing `tmp/` directory.
6. The final report identifies any non-blocking RC limitations accurately and
   contains no claim of stable history compatibility.

## Publication Gate

Reaching the definition of done makes the source and artifacts ready to
publish; it does not authorize publication.

Do not create a Git tag, GitHub Release, container-registry release, stable
channel entry, or other public release as part of this goal. Stop at the human
publication gate with:

- the exact candidate commit;
- the proposed `v0.1.0-rc.1` tag;
- the complete release-readiness report;
- the artifact list and checksums;
- the final successful CI links; and
- the exact remaining publication commands or actions.

The administrator must explicitly authorize publication in a later request.
Do not create a stable release until the administrator separately declares
that the project is ready for formal stable release and revisits the applicable
history-compatibility boundary.
