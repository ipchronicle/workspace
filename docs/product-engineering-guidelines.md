# IPChronicle 产品工程准则

Status: Accepted cross-repository baseline

Date: 2026-08-07

## 目的与适用范围

本文定义 IPChronicle 产品源码在开发、重构和维护时共同遵守的工程准则。
它适用于未来的 `ipchronicle/ipchronicle` 产品仓库，不替代 workspace 的
协作规则，也不为尚未创建的源码预设目录。

产品定义、系统架构和已接受 ADR 是产品行为与架构边界的权威来源。本文只
把这些边界转化为代码层面的执行规则；发生冲突时必须遵守 ADR，而不是用
通用工程习惯重新解释已确认决定。

产品仓库创建后，根 `AGENTS.md` 应引用或吸收这些稳定规则，并根据真实源码
补充目录所有权、生成流程和可直接执行的检查命令。不存在的目录、工具或命令
不得提前写成约定。

## 总体原则

- 优先选择显式、简单、可读的实现。抽象必须减少真实重复、保护已确认边界，
  或使复杂状态转换更容易验证。
- 不为假设中的扩展提前设计通用框架、插件层、兼容层或第二套实现。
- 保持数据流和所有权清晰。跨模块调用应当暴露领域意图，而不是共享可变全局
  状态或直接访问其他模块的存储细节。
- 修复根因。不得用静默回退、伪成功、重复事实来源或宽泛错误吞噬掩盖失败。
- 小改动保持聚焦；大改动按可验证的垂直切片推进，不顺带重构无关代码。
- 依赖数量不是单独目标。新增依赖必须说明标准工具或现有依赖为何不足，并以
  实际维护、资源、许可证和发布成本评估收益。
- 不机械追求小文件、接口数量或固定分层。函数和组件应当围绕清晰职责拆分，
  不能为了形式制造只转发调用的空壳。

## 前端规则

- 使用 React Function Components 和 TypeScript strict 模式。避免 `any`、
  未检查的类型断言和与 OpenAPI 契约重复的手写传输类型。
- 使用 Vite 进行本地开发和生产构建；生产运行时只由 Center 提供已经编译的
  静态资源，不运行 Vite 开发服务器或 Node.js 应用服务。
- 官方 shadcn/ui 源码组件是默认组件基础。页面优先使用 Tailwind CSS 工具类
  和共享主题变量；自定义 CSS 与组件遵守 ADR 0047 的必要性和范围限制。
- 管理界面中独立承担功能的内容区使用官方 `Card` 作为视觉容器，不以仅有
  分隔线的裸表单或裸数据区直接铺在页面上。页面标题、全局导航和 `Alert`
  等自身已有明确边界的全局反馈不强制套入 `Card`；`Card` 之间不得嵌套。
- 官方 block 只能作为合适结构的起点。不得为了保留示例而复制模拟数据、推广
  元素、无关路由或没有产品行为的演示交互。
- 页面组件负责展示、交互、表单体验和请求状态。权限、业务不变量、最终校验、
  持久化和任务状态转换由 center 负责。
- API 请求统一通过 ADR 0040 定义的 `openapi-fetch` transport。页面和基础 UI
  组件不得散落裸 `fetch`、硬编码接口路径或重复认证、CSRF 和错误解析逻辑。
- 可以在 transport 之上建立具有领域名称的调用函数或 hooks，但它们不能成为
  第二套 HTTP 契约，也不能隐藏后端失败为成功或空数据。
- 状态默认保持在最小所有者范围。只有多个远距离消费者确实共享同一 UI 状态
  时才提升所有权；不能因习惯引入全局状态管理。
- 表单库、服务端状态缓存库和额外 schema 库在证明确有需要后选择。客户端
  schema 只服务交互体验，不能取代 OpenAPI 传输契约或 center 的最终校验。
- 所有 IPChronicle 自有可见文本、表单反馈、空状态、错误、tooltip 和无障碍
  标签使用 ADR 0048 的翻译资源。不得先硬编码一种语言再把翻译留作清理任务。
- 原始 IPQuality JSON、诊断和用户内容保持原值；本地化标签不能伪装成原始
  数据的一部分。
- 组件应覆盖 loading、empty、offline、partial success、failure、recovery 和
  destructive confirmation 等所属工作流真实存在的状态。

## Center 规则

- Go 代码使用标准 `context.Context` 传递取消、期限和请求范围信息。不得把
  context 存入长期对象或用背景 context 绕过已有取消链。
- HTTP handlers 实现生成的严格接口并负责传输边界：读取已绑定输入、调用
  应用行为、映射明确响应。业务不变量、持久状态转换和跨步骤协调不得堆在
  handler 中。
- 领域逻辑按模块组织。只有复杂度或复用确实需要时才引入 service、repository
  或接口；简单操作不强制经过固定三层空壳。
- Chi 和 HTTP 类型停留在组合与传输边界。领域模块使用标准 context 和应用
  类型，不依赖路由上下文读取隐式输入。
- 错误必须保留可判断的类别和因果链。API 暴露稳定错误码与结构化参数，日志
  保留运维诊断，前端负责本地化；三者不能混成一段字符串契约。
- 后台工作先持久化再由有界 worker 执行。不得用内存队列替代已经要求的持久
  状态，也不得为普通并发引入外部消息系统。

## API 与生成代码

- OpenAPI 3.1 文件是管理员与 Agent HTTP 契约的唯一来源。接口变更必须在同一
  产品改动中同步契约、生成代码、实现、调用方和兼容性测试。
- 不手工编辑生成的 Go 或 TypeScript 文件。生成工具、配置和漂移检查必须可
  重现，生成失败应明确阻止合并。
- JSON 字段、错误码、状态值和资源语义由契约定义。不能依赖前后端碰巧使用
  相同手写名称维持兼容。
- WebSocket 只承担已确认的临时唤醒职责，不建立第二套任务或配置协议。
- 结构化 Webhook 与 JavaScript sender 数据保持语言无关；不得因 UI 本地化
  改变机器接口字段。

## 持久化规则

- `config.db` 与 `history.db` 保持独立所有权和迁移序列。不能通过便捷查询或
  隐式事务模糊两者边界。
- Center 使用显式参数化 SQL、`database/sql` 和 `sqlc`。SQL 放在所属模块可
  审查的 schema、migration 和 query 输入中，不直接写入 HTTP handler。
- Migration 是 schema 历史的唯一来源。ORM model、Go struct 或运行时自动
  建表不能成为并行 schema 定义。
- 不统一套用 `created_at` 与 `updated_at`。字段必须表达领域时间，例如观察、
  执行、接收、确认或状态转换时间，并定义排序和延迟到达语义。
- 外键、唯一约束和索引由不变量与查询证据驱动。不能省略必要约束，也不能为
  猜测中的查询预建大量索引。
- 跨两个 SQLite 数据库的行为使用已确认的持久幂等状态机，不模拟不存在的
  跨库原子事务。
- Agent 的 bbolt 元数据和不可变结果文件遵守 ADR 0042 的发布、同步、提交和
  启动对账顺序。不得把大结果重新存回 bbolt 或弱化崩溃一致性。

## Agent 规则

- Agent 保持无 CGO 的 Linux AMD64/ARM64 可执行文件，并在已支持的 systemd
  与 OpenRC 环境运行。不能因本地开发方便引入目标系统不可用的运行时依赖。
- 安装和服务继续要求 root。不得添加未确认的降权路径、入站监听端口或 SSH
  执行方式作为隐式兼容方案。
- 配置只有在完整验证并持久化成功后才提升 applied revision。失败必须保留
  上一个有效配置并报告明确状态。
- 任务、结果和地址事件遵守现有幂等标识、保留上限、代际和淘汰规则。重试
  上传不能重新执行探测，队列溢出不能静默丢失。
- 子进程必须具有明确的超时、进程树终止、输出大小和诊断脱敏边界。
- Agent 更新不得提前破坏旧可执行文件可读的本地状态或已引用结果文件。

## 工作与验证规则

- 修改前阅读距离目标最近的 `AGENTS.md`、相关 ADR、契约、migration 和现有
  测试，并分别检查 workspace 与产品仓库状态。
- 不回退用户改动，不修改无关文件，不把依赖目录、环境文件、数据库、构建
  产物或真实凭据加入版本控制。
- 行为不明确且会影响产品边界时先确认或新增决策；不能用 TODO 代替必要决定，
  也不能留下 TODO 后把功能描述为完成。
- 新功能同时实现类型、边界校验、失败状态、权限、安全和与风险相称的测试。
- API、schema、生成工具或组件升级必须检查所有下游消费者，不能只让一个
  包局部编译通过。
- 使用产品仓库实际定义的格式化、生成漂移、静态检查、单元、竞态、集成、
  浏览器、构建和 Compose 验证命令。不得在 `AGENTS.md` 中发明不存在的命令。
- 完成前检查 diff 中的无关改动、秘密、生成物、第二套逻辑、宽泛错误吞噬、
  未覆盖状态和未说明行为变化。

## 产品仓库 AGENTS.md 最低内容

Phase 0 创建的产品仓库根 `AGENTS.md` 至少应包含：

- 产品定义、系统架构和 ADR 的权威关系与入口；
- monorepo 内 center、Agent、web、协议、部署和测试目录的实际所有权；
- 当前真实的生成、格式化、lint、type-check、test、race、build 和 Compose
  命令；
- 生成文件位置、是否提交及禁止手改规则；
- 前端、Center、Agent、存储与 API 的上述工程边界；
- 多语言、许可证、秘密、构建产物和本地状态规则；以及
- 子目录确有不同工具或安全边界时，如何通过最近的 `AGENTS.md` 增加局部规则。

不要预先创建一组子目录 `AGENTS.md`。只有局部规则真实存在且根文件会变得
含混时才拆分。

## 保持未决的实现选择

本文不选择以下仍应在所属阶段验证的事项：

- 确切 Node.js、Vite 和 React 构建集成版本；
- React 国际化、表单和服务端状态缓存库；
- 产品源码目录名称和 Go package 布局；
- CI provider、生成文件提交策略和精确检查命令；以及
- 其他在实施顺序中明确延后的窄参数。

这些选择一旦确认，应写入适当的 ADR、产品仓库说明或最近的
`AGENTS.md`，而不是悄悄固化在脚手架默认值中。
