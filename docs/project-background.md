# IPChronicle 项目背景

## 起因

IPChronicle 的前身是 `Komari-ip-history`。旧项目最初围绕 Komari 开发，通过注入页面、节点绑定和嵌入界面补充 IP 质量探测、历史记录、快照对比和通知能力。

随着 Komari 自身重构并发布新版本，继续把新产品建立在 Komari 的页面结构、接口、主题和登录流程之上，会让核心能力长期受上游变化影响。旧项目在持续适配过程中也积累了较多跨层耦合、兼容逻辑和难以独立演进的实现。

因此决定建立独立品牌和组织 `IPChronicle`，重新讨论产品目标和整体架构，并从头实现新项目。

## 已确认事项

- 新项目名称为 `IPChronicle`。
- GitHub 组织为 `ipchronicle`。
- 新项目是独立产品，不再以 Komari 为基础。
- 新项目计划重新设计和实现，而不是在旧仓库中继续重构。
- 旧项目作为参考库保留，不作为新项目依赖。
- 本地开发以 `ipchronicle-workspace` 作为多仓库工作目录。
- 各产品仓库保持独立 Git 历史。

## 刻意留空的决策

以下内容需要由用户和新开发机中的 Codex 重新讨论，当前没有默认答案：

- 产品定位和首个版本功能范围
- 哪些旧功能保留、舍弃或重新定义
- 服务端、前端和节点端的技术栈
- 单仓库或多仓库的最终边界
- 是否需要独立 Agent
- API、认证、权限和数据模型
- 数据库、任务处理和通知架构
- 部署、升级、备份和发布方式
- 是否提供 Komari 或其他系统的可选集成
- 是否需要兼容或迁移旧项目数据

现有 `server`、`web`、`agent`、`deploy` 空仓库只是名称预留，不构成架构决定。

## 旧项目如何使用

旧项目适合用于参考：

- 用户已经使用过的操作流程
- IP 质量结果、历史和比较场景
- 安装、上报、通知和公开访问中出现过的问题
- 安全审查结论和测试覆盖清单
- Komari 强耦合带来的维护成本

旧项目不应默认用于：

- 直接复制目录结构或领域模型
- 延续已有 API 和数据库表
- 继承现有依赖与部署模型
- 以兼容旧实现为由保留复杂分支

任何代码复用都应当作为独立技术决策审查，而不是默认迁移。

## 新会话的第一阶段

新开发机会话应先完成产品与架构讨论，再开始写实现代码。至少需要明确：

1. 产品解决什么问题，首个可用版本服务哪些用户。
2. 哪些能力属于核心，哪些属于以后扩展。
3. 组件边界、数据流和信任边界。
4. 技术栈与部署约束。
5. 测试、发布和升级的最低标准。

讨论结果应写成独立文档或 ADR，使后续会话不依赖聊天记录。
