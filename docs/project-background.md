# IPChronicle 项目背景

## 起因

IPChronicle 的前身是 `Komari-ip-history`。旧项目最初围绕 Komari 开发，通过注入页面、节点绑定和嵌入界面补充 IP 质量探测、历史记录、快照对比和通知能力。

随着 Komari 自身重构并发布新版本，继续把新产品建立在 Komari 的页面结构、接口、主题和登录流程之上，会让核心能力长期受上游变化影响。旧项目在持续适配过程中也积累了较多跨层耦合、兼容逻辑和难以独立演进的实现。

因此决定建立独立品牌和组织 `IPChronicle`，重新讨论产品目标和整体架构，并从头实现新项目。

## 已确认事项

- 新项目名称为 `IPChronicle`。
- GitHub 组织为 `ipchronicle`。
- 新项目是独立产品，不再以 Komari 为基础。
- 新项目计划重新设计和实现，而不是在旧仓库中继续重构。
- 旧项目作为参考库保留，不作为新项目依赖。
- 本地开发以 `ipchronicle-workspace` 作为多仓库工作目录。
- 各产品仓库保持独立 Git 历史。

## 首版架构基线

项目最初刻意留空了产品范围、技术栈、Agent、数据、部署、仓库和发布
边界。这些首版决策现已完成讨论并形成可实施基线：

- [产品定义](product-definition.md) 汇总首版用户、功能和明确排除项。
- [系统架构](system-architecture.md) 汇总组件、数据流、信任边界和技术
  约束。
- [架构一致性审查](architecture-baseline-review.md) 记录基线审查范围、
  已关闭的冲突和实施就绪边界。
- [架构决策记录](decisions/README.md) 是各项长期决定及其理由的权威
  来源。
- [首版实现顺序](implementation-sequence.md) 说明如何按可验证的垂直
  切片实现这些决定。
- [产品工程准则](product-engineering-guidelines.md) 将已确认边界转化为未来
  产品仓库的代码和验证规则，不预设尚未创建的源码目录。
- [UI 信息架构](ui-information-architecture.md) 记录首版界面已经确认的页面
  职责、导航关系和仍待确定的交互边界。

产品源码采用单一 `ipchronicle/ipchronicle` 仓库。现有 `server`、`web`、
`agent`、`deploy` 预留仓库不构成首版组件边界，也不应为了利用预留名称
而拆分实现。

## 旧项目如何使用

旧项目适合用于参考：

- 用户已经使用过的操作流程
- IP 质量结果、历史和比较场景
- 安装、上报、通知和公开访问中出现过的问题
- 安全审查结论和测试覆盖清单
- Komari 强耦合带来的维护成本

旧项目不应默认用于：

- 直接复制目录结构或领域模型
- 延续已有 API 和数据库表
- 继承现有依赖与部署模型
- 以兼容旧实现为由保留复杂分支

任何代码复用都应当作为独立技术决策审查，而不是默认迁移。

## 当前阶段

产品与架构讨论阶段已经完成，单仓库产品实现位于
`repos/ipchronicle`。首个稳定版 `v0.1.0` 已于 2026-09-03 发布；其
`config.db`、`history.db` 和 Agent 本地状态构成初始持久数据兼容基线。
新会话应先阅读上述基线文档和最新 ADR，再检查 workspace 与产品仓库状态。Go、Node.js、
OpenAPI、数据库和部署选择已经进入产品仓库；实现不得重新打开已经确认的
产品、数据所有权、信任、部署或兼容边界。

任何会改变这些长期边界的实现发现都需要新增或取代 ADR，而不是通过
代码中的兼容分支悄悄改变架构。

`v0.1.0` 之前的开发版本和 RC 数据仍不属于受支持升级来源。`v0.1.0`
及后续受支持稳定版本的数据必须遵循向前迁移、Agent 回滚和发布兼容测试
要求；损坏或不兼容的数据必须明确失败，不能被静默替换。ADR 0058 记录
发布前边界，ADR 0068 记录稳定版兼容基线。
